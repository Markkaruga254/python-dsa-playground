# Assessment and readiness guide

## Why assessment exists

The purpose of assessment is to establish whether a learner can apply a concept independently. A quiz score or accepted online submission is useful evidence, but neither is sufficient on its own.

Use the rubric below for weekly reviews, mock interviews, and self-assessment. Be honest about hints, copied code, and unfinished work.

## Problem-solving rubric

Score each category from zero up to its maximum.

| Category | Points | What good performance looks like |
|---|---:|---|
| Correctness | 30 | The solution meets the stated requirements and works on representative cases |
| Complexity analysis | 20 | Time and auxiliary-space complexity are stated and justified |
| Explanation | 20 | The learner explains the approach, data structures, and important decisions clearly |
| Edge cases and testing | 15 | The learner identifies and tests meaningful boundary and failure cases |
| Independence | 15 | The learner develops the solution without copying; any hints or references are disclosed |
| **Total** | **100** | |

### Interpreting a result

- **85–100 — Strong:** correct, well-explained, tested, and independently implemented.
- **70–84 — Pass with follow-up:** core understanding is present; record and revisit the weaker category.
- **Below 70 — Revisit:** review the concept, study a worked example, and retry a similar problem later.

A score is not a substitute for judgement. A solution that does not work on the stated requirements cannot be treated as mastered, even if the other categories score well. For a weekly checkpoint, aim for at least 70/100 and a correct implementation.

## Hint and independence record

Record the highest level of help used:

- **H0 — Independent:** no hints, editorials, or solution references.
- **H1 — Prompt:** a small nudge about the relevant concept or pattern.
- **H2 — Guided:** a sequence of hints or help identifying the algorithm.
- **H3 — Reference:** inspected an editorial or existing implementation.

Using help is part of learning; hiding it makes progress harder to measure. After H1–H3, close the reference and reimplement from a blank file. Reattempt the problem after a delay and record whether it is now H0.

## Weekly review

At the end of each week:

1. Select three representative problems: one foundational, one typical, and one that exposed a weakness.
2. Re-solve them without notes or previous code.
3. State time and auxiliary-space complexity.
4. Test at least one normal case and two meaningful edge cases where applicable.
5. Explain one solution aloud as if in an interview.
6. Record quiz results, hint levels, and topics to revisit in the week's review file.

Do not advance merely to preserve a calendar streak. If the core pattern is still unclear, spend another session on it.

## Mock interview protocol

For a timed mock, use this sequence:

1. Clarify the input, output, constraints, and ambiguous requirements.
2. Work through a small example and identify edge cases.
3. Explain a straightforward approach before optimising.
4. Choose a data structure and justify it.
5. Implement readable code.
6. Trace the implementation and test it.
7. Analyse time and auxiliary-space complexity.
8. Discuss trade-offs and possible improvements.

A mock should assess communication and reasoning as well as code. Record the time spent, where progress stalled, hints used, and one concrete improvement for the next attempt.

## Suggested readiness evidence

A learner is approaching interview readiness when they can repeatedly:

- Solve representative easy problems independently.
- Recognise common patterns without forcing every problem into a memorised template.
- Implement medium-level problems with a clear plan and sensible tests.
- Explain complexity and trade-offs accurately.
- Recover from a wrong first approach by reasoning from constraints and examples.

This course is a practice resource, not a certification or a guarantee of passing any employer's assessment.
